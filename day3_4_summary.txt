CHALLENGE 1 - Kink direction (OPEN-1)

  Problem: at the straight-arm pose the upper arm leans 8.13 deg to one side.
  A mirror-image model (leaning the other way) has identical lengths, reach,
  and code-vs-URDF agreement, so NO test can tell the two apart.
  If it were mirrored, a "tilt shoulder 30 deg forward" command would actually
  land the arm at 22 deg instead of 38 deg from vertical - a 16 deg error,
  roughly 21 cm at the gripper. Pick-and-place would miss every time.

  Resolved: positive shoulder angle tips the arm further in the direction it
  already leans (student, from the manual), and Figure 3 shows the elbow
  offset on the side the arm reaches toward. Both match the model.
  Still: 30-second check on hardware.

CHALLENGE 2 - Getting the manual

  The Studocu link returned HTTP 403 (and was a profile page, not the file).
  Resolved by attaching the PDF (QArm User Manual V2.1, 7 April 2021).

CHALLENGE 3 - The manual gives TWO different reach figures

  Section B (Configuration):  0.800 m horizontal, 0.940 m vertical
  Section D (Workspace):      0.7536 m horizontal, 0.8936 m vertical

  Our chain to end_effector:  0.753553 m          0.893553 m

  Section D matches our model EXACTLY - independent confirmation of L1..L5,
  beta and the DH table from Quanser's own numbers. This is stronger evidence
  than anything we had on Day 2.

  Section B is larger by the same 46.4 mm in both directions. On Day 2 we
  ASSUMED that was the fingertip; the manual never says so.

  Decision (option 1): Section B is measured to the fingertips. Keep
  gripper_tip at 46.4 mm past end_effector. Docs now say this is our reading
  of the manual, not a statement from it. Measure on hardware.

CHALLENGE 4 - The joint limits did not fit our zero (the main finding)

  The manual says Figure 3 is the HOME POSE: upper arm up, forearm
  HORIZONTAL. Figure 4b "Home Configuration" shows the same. Quanser's joint
  ranges (Table 7: -170/170, -85/85, -95/75, -160/160) are measured from it.

  Our old zero was "arm dead straight", forearm in line with the upper arm.
  To reach the manual's home pose our elbow had to bend 81.87 deg (90 - beta).
  Running FK proved the mismatch:

      qarm_fk 0 0 81.87 0 --no-limits  ->  end_effector (0.450, 0, 0.490)
                                            = Figure 3 home pose exactly
      qarm_fk 0 0 81.87 0              ->  error: joint_3 = 81.87 deg is
                                            outside its limits [-95, 75]

  The model could not reach the arm's own home pose.

  Also corrected a wrong claim in our docs: "symmetric ranges transfer
  regardless of where zero sits" is FALSE. If a zero is offset, a symmetric
  range becomes asymmetric in the other convention. It only works if the
  zeros coincide (true for base, shoulder, wrist; false for the elbow).

  Student confirmed: positive elbow swings the forearm DOWN toward the table,
  the same direction as ours. So the two conventions differ by a constant:
      our_old_elbow = quanser_elbow + 81.87 deg

  Two options:
    A) keep our zero, convert the limits to -13.13 .. +156.87 deg.
       Smallest change, but every hardware reading needs a +81.87 deg
       conversion forever - an easy thing to forget.
    B) adopt Quanser's zero. Limits stay exactly as printed in Table 7, and
       angles pass between hardware, URDF, FK and IK unchanged.
  Chose B.

  What B changed:
    URDF   joint_3 origin rpy: (0, beta, 0) -> (0, pi/2, 0)
           pi/2 = beta + (90 deg - beta): the structural kink is still
           applied exactly once, plus the 81.87 deg home-pose offset.
    DH     row 3 theta: q3 + pi/2  ->  q3 + pi - beta
           Read it as (q3 - ELBOW_STRAIGHT) + pi/2, where
           ELBOW_STRAIGHT = beta - 90 deg = -81.87 deg is the elbow angle at
           which the arm is dead straight. The bracket is the bend measured
           from straight (the old q3); + pi/2 is the same bookkeeping as before.
    Limits unchanged numerically: -95 .. +75 now means what Table 7 means.

  WHY THE NEW -beta IN ROW 3 IS NOT THE DAY 2 BUG:
    The Day 2 bug applied the kink's LENGTH twice and shortened the upper arm
    (353.6 -> 346.5 mm). Here no length changes: a_2 is still lambda_2 and
    row 3 has d = a = 0. The -beta only says where the elbow's zero points:
    row 2 aims along lambda_2 (tilted +beta), but the elbow measures from L2
    (not tilted), so row 3 rotates back by beta.
    test_kink_applied_exactly_once still guards the length.

  New zero pose, q = [0, 0, 0, 0] (= manual home pose):
      end_effector  (0.450000, 0.000000, 0.490000) m,  RPY (0, 90 deg, 0)
      gripper_tip   (0.496447, 0.000000, 0.490000) m
  This is Figure 3 read directly: L3 + L4 + L5 = 0.45 m across the top,
  L1 + L2 = 0.49 m up the side.
  The Day 2 straight-arm numbers (0.106569, 0, 0.885980) still hold, now at
  q = [0, 0, -81.87 deg, 0].

CHALLENGE 5 - RPY readout broke at the new home pose (found by the change)

  The home pose points the tool horizontally: pitch = 90 deg exactly, which is
  RPY gimbal lock. rpy_from_transform computed cos(pitch) as sqrt(1 - sin^2);
  1e-16 of rounding in sin became 1e-8 in cos, missed the gimbal-lock test,
  and printed the home pose as (180, 90, 180) deg - the same orientation, but
  confusing. Fixed with cos(pitch) = hypot(R[0,0], R[1,0]). Now (0, 90, 0).
  The Day 2 review had noted this branch was untested; the zero-pose test
  now exercises it.

CHALLENGE 6 - Gripper: "the stub" was misread (assistant error)

  The assistant took "same length as the stub" to mean the 46.4 mm
  gripper_tip extension. The student meant the 15 cm L5 cylinder between the
  wrist and end_effector. Corrected, then two drawings were offered:
    A) fingers inside the 15 cm, fingertips at end_effector
       (would contradict the Section B reach)
    B) body over the 15 cm, fingers 46.4 mm past it to gripper_tip
       (matches Section B)
  Chose B.

  Design:
    - L5 cylinder = gripper body, red palm crossbar at its end.
    - Two straight fingers, end_effector -> gripper_tip, sliding along the
      end effector's y axis.
    - finger_left_joint (prismatic, 0 = closed .. 0.020 m = open) and
      finger_right_joint MIMICS it, so one number drives both fingers, like
      the real gripper's single motor. Gap 0 .. 40 mm.
    - Full stroke in 1 s, from Table 7's gripper speed (100 %/s).
    - end_effector and gripper_tip did not move; FK is untouched.

  Toggle:
    - New node qarm_gripper: subscribes std_msgs/Bool on /gripper/command
      (true = open, false = close), publishes the finger positions on
      /gripper/joint_states, ramped at the real gripper's speed.
    - joint_state_publisher_gui merges /gripper/joint_states into
      /joint_states via its source_list parameter, so the toggle (not the
      slider) drives the fingers. Works with or without the GUI.
    - The node lives in qarm_description/scripts/, not qarm_kinematics,
      because the display launch file would otherwise make qarm_description
      depend on qarm_kinematics, which already depends on qarm_description -
      a circular dependency colcon would reject.
    - First test run failed pep257 D213 (multi-line docstring summary must
      start on the second line). Fixed.

CHALLENGE 7 - Tooling (assistant side, worth knowing)

  - Commands run from Windows PowerShell into WSL did not return their output
    reliably, so every check wrote to a log file under .agents/ and was read
    back from there. Reads sometimes happened before the command finished.
  - A ros2 launch started in the background of a script IGNORES Ctrl+C
    (non-interactive bash disables SIGINT for background jobs), so the
    headless gripper test left robot_state_publisher and the gripper node
    running. Cleaned up; confirmed nothing left behind.
  - "pkill -f <pattern>" also matched (and killed) its own shell, because the
    pattern was in its own command line. Use "grep '[p]attern'" tricks or
    PIDs instead.
