================================================================================
        2. REVIEW OF COMMIT aba1774 (THE BRIDGE)
================================================================================

aba1774 added hardware_bridge.py, fake_qarm_hardware.py, hardware.launch.py
and the start_from_measured mode in move_to_node.py. Lint and the unit tests
pass. Findings, worst first:

2.1  LIMIT BUG - CAN SEND THE ARM HOME. NOT FIXED.
     command_to_quanser() rejects any value even slightly past a limit.
     Reproduced: the SLEEP_POSE example in the launch file uses 1.309 rad for
     the elbow, which is 3e-6 rad past +75 deg, so it is rejected:
         joint_3 = 1.3090 rad (75.00 deg) is outside [-95.00, 75.00] deg
     Chain of events: Quanser's driver starts commanding home (all zeros) ->
     move_to reads the out-of-limit pose and tries to hold it -> the bridge
     drops every hold command -> the driver keeps its zero command -> the arm
     stands up to home. An encoder resting on a hard stop can read slightly
     past a limit for the same reason. Fix: a small tolerance (about 0.5 deg)
     for measured poses, or refuse to start loudly. Note Quanser's own
     SLEEP_POSE (15*pi/36) is exactly on the elbow limit.

2.2  hardware_bridge.py docstring says "Field sheet step 4.4 confirms that on
     the real arm" about the gripper mapping. Step 4.4 has not been done.
     Remove the sentence until it has.

2.3  move_to/done means "finished commanding", not "arrived". On hardware the
     arm lags behind the command. Anything sequencing moves should check
     /joint_states. Document it at least.

2.4  Launch order is not guaranteed. If qarm_hardware starts well before
     qarm_move_to, the arm travels further toward home than the docstring's
     "fraction of a second". The docstring warns about it.

2.5  initial_pose with mixed ints and floats ("[0, -1.4835, 1.309, 0]")
     fails parameter typing because value_type=None. Fake driver only.

2.6  "Is the bridge and qarm_hardware running?" should be "Are".

      L_1..L_5 = 0.14, 0.35, 0.05, 0.25, 0.15. LAMBDA_3 = L_4 + L_5.
      Identical to robot_params.py. forward_kinematics, inverse_kinematics
      (4 solutions + best), differential_kinematics (Jacobian), input helpers.
  5_research/qarm/ROS Examples/ros2/src     about 540 lines in total
      qarm_hardware.py   driver node, 200 Hz, /qarm/joint_position_cmd,
                         /qarm/gripper_cmd, /qarm/led_cmd -> /qarm/joint_states
      move_qarm_server   action: x, y, z, wrist -> Quanser IK -> command
      rgbd.py            RealSense publisher
      qarm_interfaces    MoveQArm.action, QArmDiagnostics.msg

Behaviours of Quanser's ROS driver that matter for safety:
  - Commands home (all zeros) the moment it starts.
  - Gripper command starts at 0 -> clipped to 0.1 -> gripper OPENS on start.
  - No command checking at all.
  - cmd_timeout_sec is declared and never used: no command timeout.
  - Ctrl+C closes the USB connection. What the arm does then is not stated.
  - move_qarm_server's wait loop has no timeout.
  - Quanser's IK returns [0,0,0,0] when no solution is in limits, which is
    also the home pose. Code that does not check for it sends the arm home.

        6. THE LAB PC IS WINDOWS - WHAT THAT CHANGES
================================================================================

The arm must be driven from the lab PC because of the Quanser licence. That
PC has Windows only. Consequences:
  - Our ROS stack (bridge, move_to, RViz) cannot run next to the arm.
  - Quanser's pal library runs on Windows and is all that is needed.
  - Our kinematics package needs only Python and numpy. robot_params.py,
    forward_kinematics.py, inverse_kinematics.py and __init__.py have no ROS

Install notes (from the co-op guide and Quanser's docs):
  - Python 3.10.11. The guide says the libraries fail on newer versions.
  - Quanser SDK for Windows, or QUARC (which already includes it).
  - Python API: run install_quanser_python_api.bat in
    C:\Program Files\Quanser\Quanser SDK\python  (or ...\QUARC\python).
    The pip/%QSDK_DIR% route failed today because of PowerShell vs cmd and a
    literal "<version>" placeholder.
  - Quanser Academic Resources in C:\Users\<user>\Documents\Quanser.
  - A failed "import quanser" can also mean the arm is switched off.
  - Check: python -c "import quanser.hardware, quanser.multimedia, numpy"
  - Status at end of day: the lab says it is installed; the import still

        8. NEW SCRIPTS FOR THE REAL ARM
================================================================================

8.1  scripts/part4.py  (commit bb4058b)
     Field sheet Part 4 on Windows through pal. Reads the measured pose and
     HOLDS it before moving (no jump to home), refuses any step over 15 deg,
     prints measured angles after each command. Opens the gripper on start.

8.2  scripts/ik_test.py  (commit 6cd9d7f)
     Drives the real arm with OUR IK. Type x,y,z in metres [,wrist deg]. It
     moves only if all four gates pass:
       1. Quanser's IK has the same solution, within 0.5 deg
       2. Quanser's FK of our angles lands within 1 mm of the target
       3. the angles are inside pal's LIMITS_MIN / LIMITS_MAX
       4. the user types y
     Holds the pose on start, steps at most 5 deg per command, logs every
     move to ik_test_log.csv (target, commanded, measured, error) for the
     accuracy table. --dry-run runs the gates with no arm.
     A ready-to-copy folder is at C:\Users\elilt\qarm_test (ik_test.py plus
     the qarm_kinematics folder) for a USB stick.

8.3  Dry run of ik_test.py against Quanser's real hal/pal on the 24.04
     distro:
       0.45,0,0.49         all gates pass, ours vs Quanser 5.1e-14 deg
       0.3,0.2,0.5         pass, [33.69, -14.52, 13.28, 0] deg from both
       0.3,-0.2,0.2,30     pass, [-33.69, 4.85, 40.49, 30] deg from both
       -0.3,0,0.3          our IK refuses: every solution breaks a limit

        9. OUR CODE VS QUANSER'S
================================================================================

  Area                          Ours                      Quanser
  USB driver                    uses Quanser's            pal QArm, ROS driver
  FK / IK                       own, same answers         QArmUtilities
  Jacobian                      no                        yes
  Move to a point               move_to_node (ROS)        move_qarm action
  Simulation                    RViz view + fake driver   QLabs (licensed)
  URDF / TF / RViz              yes                       no
  Collision geometry            shapes, no checker        no
  Command safety checks         yes                       no
  Tests                         45                        none
  Camera                        no                        RealSense via pal
  Runs on the Windows lab PC    the two scripts only      yes
  Tested on the real arm        no                        yes

Where our IK is better than Quanser's, with the same answers: it raises a
named error with the reason instead of returning [0,0,0,0]; it tells you
when a target is too far (the co-op guide lists "math error" from millimetre
input); it supports a fingertip target frame; it keeps the base angle for a
target straight overhead; it has tests. Where Quanser's is ahead: it has a
Jacobian and has been run on real arms.

How the work is split from now on:
  Ours:     IK, geometry and limits, safety (hold, small steps, refusals),
            pick-and-place sequence, camera-to-arm conversion.
  Quanser:  the USB driver, an independent check on our IK, reading the
            camera.
